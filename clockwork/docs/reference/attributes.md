# Clockwork code and build file generation

Clockwork uses rust-like attributes on files and statements to tell the compiler what code to generate from each source file.
Inner attributes (prefixed with “#!”) apply to the entire source file.
Outer attributes (prefixed with “#”, no “!”) apply to the next statement in the source file.
Note that when an attribute can be either inner or outer, the outer attribute overrides the values set in inner attributes, but only for the next statement in the source file.

> [!NOTE]
> Clockwork also has an original file format that adds more boilerplate.
> The format described in this document is recommended for new development.
> See the [original reference](legacy_repr_iface.md) to learn about the original language format.

These attributes are also integrated with Gazelle, the build file generation tool used in Clockwork, to automate generating Clockwork build files.

## Telling the compiler what code to generate

The `generate` attribute is used to tell the compiler what code to generate from each Clockwork file.
Each Clockwork file needs a `generate` attribute even if it doesn't generate any code.
The following shows the contents of `example1.clk` which defines a constant that is only used in other Clockwork files.

```python
// example1.clk: Define a constant

#![generate()]

MAX_NAME_LEN: UInt64 = 128;
```

Since no code is generated, the Bazel rule to compile `example1.clk` would be this:

```bazel
clk(
    name = "example1_clk",
    srcs = ["example1.clk"],
    generate = ["none"],
)
```

The above build rule is automatically generated by Gazelle when it sees a Clockwork file that has a `generate` attribute in the source directory.

If you wanted to define a schema and generate C++ then you would add `cpp` to the generate target.
Additionally, the compiler needs to know the namespace to use for C++, so you also need a `cpp` attribute.
The following shows the contents of `example2.clk` which defines a simple schema and generates C++.

```python
// example2.clk Define a simple schema

#![generate(cpp)]
#![cpp(namespace=clockwork::example)]

// A simple schema
schema SimpleSchema {
  fields
  {
    // The string UUID of the cog to be assigned to a gpu
    #1 int32_field: Int32;
  }
}
```

Then when Gazelle runs it will generate the build file automatically.

```bazel
clk(
    name = "example2_clk",
    srcs = ["example2.clk"],
    outs = [
        "example2_clk_cc.cc",
        "example2_clk_cc.hh",
        "example2_clk_cc.inl",
    ],
    generate = ["cpp"],
)
```

## Generate attributes

Clockwork can generate a lot more than just simple C++ schema wrappers.
This is the complete list of targets that can appear in a `generate` attribute.

`cpp`
: Generate C++ from the Clockwork file.

`py`
: Generate python from the Clockwork file.

`nanobind`
: Generate nanobind from the Clockwork file.

`proto`
: Generate C++ and python Protobuf wrappers from the Clockwork file.

`go_proto`
: Generate Go language Protobuf wrappers from the Clockwork file.

`proto_conv`
: Generate C++ converters to convert between Protobuf and C++ (requires that the `cpp` and `proto` targets are also generated).

`cpp_cog`
: Generate a C++ cog (requires that the `cpp` target is also generated).

`cpp_exe`
: Generate a C++ executable.

`py_cog`
: Generate a python cog.

`py_exe`
: Generate a python executable.

Each of the above targets is covered in detail later in this document.
It is important to note the a Clockwork file can have more than one target in the `generate` attribute.
For example, if we also wanted to generate python for the schema defined in `example2.clk` we just need to change the `generate` attribute to the following.
The rest of the file stays the same.

```python
#![generate(cpp, python)]
```

And then Gazelle will generate the build file for you.
Here is one final build file example showing the generated build file.

```bazel
clk(
    name = "example2_clk",
    srcs = ["example2.clk"],
    outs = [
        "example2_clk_cc.cc",
        "example2_clk_cc.hh",
        "example2_clk_cc.inl",
        "example2_clk_py.py",
    ],
    generate = [
        "cpp",
        "py",
    ],
)
```

## Importing definitions from other Clockwork files

The `use` statement imports definitions from other Clockwork files.
Additionally, Gazelle parses the `use` statements to generate the dependencies needed in the build files.

> [!NOTE]
> This section is only for Clockwork files that contain a `generate` attribute.
> See the [original use statement reference](legacy_use.md) to learn about the original language format.

The simplest form of the `use` statement imports the definitions from another Clockwork file implicitly adding dependencies for the targets found in the `generate` attribute.
For example, the following will import C++ and python bindings for the contents of `example2.clk`.

```python
#![generate(cpp, py)]
#!cpp(namespace=clockwork::example)]
use clockwork::example::example2;
```

Note that this will add a dependency for both python and Clockwork from `example2.clk`.
If you tried to do that with `example1.clk` you would get an error because `example1.clk` doesn't generate anything.
You can add a list of targets to the `use` statement to make the dependencies explicit.
An empty list of targets tells Clockwork not to add any language specific dependencies.
For example, the `use` statements to get `cpp` from `example2.clk` and nothing from `example1.clk` would look like this:

```python
#![generate(cpp, py)]
#!cpp(namespace=clockwork::example)]
use[] clockwork::example::example1;
use[cpp] clockwork::example::example2;
```

By default the `use` statement makes everything defined in a Clockwork file available.
The objects imported are referenced by prefixing with the name of the import module.
For example, a reference to the maximum name length defined in `example1.clk` would be `example1::MAX_NAME_LEN`.

You can avoid having to prefix the imported definitions by adding an explicit list of what you want to import.
The following would import just `MAX_NAME_LEN` and make it accessible without any prefix.

```python
use[] clockwork::example::example1::{MAX_NAME_LEN};
```

Those curly brackets are an artifact of Gazelle integration, which needs a way to tell the imported definitions from the module names.

You can also apply aliases to both the imported modules and the objects imported.
For example, the `use` statement to import from `example1.clk` and access the imported objects with an alias could be:

```python
use[] clockwork::example::example1 as example_alias;
```

Then the max name length would be referenced as `example_alias::MAX_NAME_LENGTH`.

And the `use` statement to import max name length and call it something else could be:

```python
use[] clockwork::example::example1::{MAX_NAME_LEN as SOME_ALIAS};
```

## Parameterized schemas

The Clockwork compiler cannot generate code for a parameterized schema until the schema has been instantiated.
Instantiating a schema tells the compiler to generate code for the schema with a specific set of parameters and optionally what to name the instantiation.
For example, consider a simple parameterized schema in `example3.clk`.

```python
// example3.clk: Simple parameterized schema

#!generate(cpp, python, nanobind)
#![cpp(namespace=clockwork::example)]

use[] clockwork::example::example1::{MAX_NAME_LEN};

schema NameSchema
{
  parameters
  {
    name_len: UInt32 = MAX_NAME_LEN;
  }
  fields
  {
    name: VarString<max_size=MAX_NAME_LEN>;
  }
}

instantiate NameSchema<>;
instantiate LongNameSchema: NameSchema<name_len=12000>;
```

The above example defines a simple parameterized schema and provides a default value for the `name_len`.
The `instantiate` statements tell the compiler to generate code for two types.
The first type is named `NameSchema` and uses the default schema parameters.
The second type is named `LongNameSchema` and uses a longer maximum name length.

The first instantiation is referenced in C++ code as `Tappy<NameSchema<>>`, and the name in other languages is just `NameSchema`.
The second instantiation is referenced in C++ code as `Tappy<LongNameSchema>` and the name in other languages is just `LongNameSchema`.

## Generating C++

Adding the `cpp` target to the `generate` attribute enables code generation for C++.
Additional information for C++ code generation is defined in a `cpp` attribute.
Any module that generates C++ needs to set the C++ namespace.
Other attributes are only required for `extern_type` or `strong_type` statements.
Note that the cpp attributes can either be inner or outer, however the namespace must be specified in an inner attribute.
Generating code into multiple C++ namespaces from a Clockwork file is not supported.

The parameters on the `cpp` attribute are:

`namespace`:
The C++ namespace for the code generated by the source file.
All generated code must go into the same namespace.

`type_namespace`:
The C++ namespace of a type referenced in an `extern_type` or `strong_type` definition.

`type_header`:
The header file for a type referenced in an `extern_type` or `strong_type` definition.

`type_factory`:
Factory function used to construct instances of types referenced in a `strong_type` definition.

The following example, `example4.clk` shows how to use the `cpp` attribute to generate C++ from Clockwork.

```python
// example4.clk: cpp attributes example

#![generate(cpp)]
#![cpp(namespace=”clockwork::example”)]

// External strong type is an alias for UInt32 with special handling in C++.
#[cpp(type_namespace=”clockwork::strong_type”, type_header=”@clockwork/external/strong_type.hh”, type_factory=”make”)]
strong_type ExternalStrongType
{
  underlying_type: UInt32;
}

// ExternType is a type defined in C++ that is used within Clockwork
#[cpp(type_namespace=”clockwork::extern_type”, type_header=”@clockwork/external/extern_type.hh”)]
extern_type ExternType;
```

The generated C++ files and build rule names are generated by adding a `_clk_cc` suffix to the stem of the Clockwork file.
For example, `example.clk` would produce C++ in `example_clk_cc.cc`, `example_clk_cc.hh` and `example_clk_cc.inl`.
The build rule that compiles the C++ library is named `example_clk_cc`.

## Generating python and nanobind

Generating python and nanobind is as simple as adding `py` and or `nanobind` to the `generate` attribute.

The generated python files and build rule names are generated by adding a `_clk_py` suffix to the stem of the Clockwork file.
For example, `example.clk` would produce python in `example_clk_py.py`.
The build rule that compiles the python library is named `example_clk_py`.

The generated nanobind files and build rule names are generated by adding a `_clk_nb` suffix to the stem of the Clockwork file.
For example, `example.clk` would produce nanobind in `example_clk_nb.cc`.
The build rule that compiles the nanobind library is named `example_clk_nb`.

## Generating Protobuf and Protobuf conversion

Adding the `proto` target to the `generate` attribute tells the compiler to generate Protobuf definitions from the contents of the Clockwork file.
Clockwork also supports generating Go language libraries which is enabled when the `go_proto` target is also set.
The `go_proto` target can only be generated when the `proto` target is also generated.

Additional information for Protobuf code generation is defined in a `proto` attribute.
Any module that generates Protobuf needs to set the Protobuf package.
In addition, generating `go_proto` requires a second name for the go language library.

The parameters on the `proto` attribute are:

`package`:
The package name to use for the C++ and python Protobuf libraries.

`go_package`:
The package name to use for the Go language Protobuf library (if generating `go_proto`).

`validate`:
Validate that all values in the protobuf are set.

`prefix_enum_value_names`:
Use the enum name and the value name to generate an upper snake case name for enum values in protobuf files.

The primary use case for Protobuf in Clockwork is for using text Protobuf files to supply configuration during initialization.
Generating conversion between C++ and Protobuf is enabled with the `proto_conv` target.
Generating the `proto_conv` target requires that the `cpp` and `proto` targets are also set in the `generate` attribute.
The `proto_conv` attribute is used to customize what code to generate for conversion.
The default is to generate code to translate from C++ to Protobuf and also from Protobuf to C++.
The `tap_to_protobuf` flag controls whether to generate a converter from C++ to Protobuf.
The `protobuf_to_tap` flag controls whether to generate code from Protobuf to C++.

In some cases, one may want to validate that all fields in a proto object have been set prior to converting it to Tachyon.
The `proto` attribute has a validate flag which defaults to true that checks that all fields have been set.

By default Clockwork uses named from the source file in the generated enumerations in protobuf files.
In some cases it is desireable to prefix the protobuf name with the type into upper snake to allow for using the same enum value name in more than once place within a package.
The proto attribute has a `prefix_enum_value_names` flag can be set to true to enable the value name prefixes.

```python
// example5.clk: Generate protobuf and protobuf conversion

#![generate(cpp, proto, proto_conv)]
#![cpp(namespace=clockwork::python::tests)]
#![proto(package=clockwork.python.tests.support.proto)]
#![proto_conv(tap_to_protobuf=false)]

// Example configuration
schema ExampleConfig
{
  uuid: 71c8779e-9c74-4812-bb86-c5aa2eb7cd50;

  fields
  {
    // Configuration string
    #1 config_string: VarString<255>;
  }
}
```

The above example will produce the Protobuf and C++ code for the Clockwork schema and also generate a converter to translate from Protobuf to C++.

The generated Protobuf files and build rule names are generated by adding a `_clk_proto` suffix to the stem of the Clockwork file.
For example, `example.clk` would produce a Protobuf file names `example_clk_proto.proto`.
The C++ Protobuf library header file would be `example_clk_proto.pb.h` and the build rule for the C++ protobuf library would be `example_clk__proto_cc_library`.
Likewise, the generated proto_conv files and build rules are named by adding a `clk_proto_conv` suffix to the stem of the Clockwork file.
The C++ Protobuf conversion library would be named `example_clk_proto_conv` and the header file would be `example_clk_proto_conv.hh`.

## Generating C++ cogs

The `cpp_cog` generate target tells the compiler to generate code for cogs defined in the source file.
Generating `cpp_cog` also requires generating `cpp` and a C++ namespace is also required.

The following example, `example6.clk`, shows the definition of a cog that runs at initialization and publishes a message.

```python
// example6.clk: C++ cog example

#![generate(cpp, cpp_cog)]
#![cpp(namespace=clockwork::example)]

use clockwork::example::example2;
use clockwork::example::example4;
use clockwork::example::example5;

//
cog ExampleInitCog
{
  configs
  {
    config : Tappy<example5::ExampleConfig>;
  }
  states
  {
    state: Tappy<example4::ExternType>
    {
      mutable: true;
    }
  }
  outputs
  {
    output: Tappy<example2::SimpleSchema>;
  }
  execution
  {
    execute when: init;
  }
}
```

The dial for the generated cog goes into a target named `<source_stem>_clk_cc_dial`.
The dial header is named `<source_stem>_clk_cc_dial.hh`.
The code to for the cog implementation needs to go into a Bazel target named `<source_stem>_clk_cc_impl`.

## Generating C++ executables

The `cpp_exe` tag tells the compiler to generate code for a C++ executable.
The compiler will generate an executable whose casing contains all of the boxes declared in the source file.
At least one box is required to generate a C++ executable.

The following example declares a box to create an instance of the C++ cog declared in the previous example and then configures the cog to run on a CPU.

It needs some extra stuff to declare a CPU domain and create a channel for the output from the initialization cog.
See the [schemas, representations, and interfaces concept guide](../concepts/schema_repr_iface.md) for mode details.

```python
// example7.clk: Example C++ executable

use clockwork::example::example2;
use[cpp, proto, proto_conv] clockwork::example::example5;
use clockwork::example::example6;

cpu_domain LocalHost;

// Example output channel
channel ExampleOutputChannel
{
  name: "/example/output";
  message_type: Tachyon<example2::SimpleSchema>;
  max_num_messages: 10;
}

box ExampleCogs
{
  new init_cog: example6::ExampleInitCog;

  new memory: HeapMemory(max_size=300'000'000);
  new config: SerializedDataFile(representation=Protobuf<example5::ExampleConfig>, path="path/to/file/example_config.pbtxt");
  new state: State(representation=example2::ExternalState, memory_resource=memory, init=init_cog.state);

  connect config to init_cog.config;
  connect init_cog.output to ExampleOutputChannel;
}

box ExampleExe
{
  new cogs_box: ExampleCogs;
  new example_proc: Process(executable=example7_clk_exe);
  apply HostProcess(process=example_proc) in cogs_box;
  apply HostCpuDomain(cpu_domain=LocalHost) to cogs_box;
}
```

One thing to note is that in the line to create `example_proc` the executable parameter is the name of the executable generated from the example file, in this case `example7_clk_exe`.

## Generating python cogs

Clockwork cogs can also be implemented in python by using the `py_cog` generate target.
Generating `py_cog` requires that `cpp` also be generated, but `cpp_cog` and `py_cog` targets cannot be generated from the same source file.

All of the types used in a python cog must have either `python` or `nanobind` wrappers.
The type of wrapper used in the cog is determined by the `py_cog` inner attribute.
All cogs declared in the source file must use the same wrapper type, which defaults to `python`.
The following line tells the compiler to use `nanobind` wrappers instead of `python`.

```python
#![py_cog(wrapper_type=nanobind)]
```

The folowing example, `example8.clk`, declares a python cog similar to the C++ cog declared in `example6.clk` above.
Python cogs cannot use C++ external types for state.
Python cogs use the built-in `PythonState` dictionary to store internal state.

```python
// example8.clk: Python cog example

#![generate(cpp, py_cog)]
#![cpp(namespace=clockwork::example)]

use[cpp] clockwork::python::python_state::{PythonState};
use[cpp, py] clockwork::example::example2;
use[cpp, py] clockwork::example::example5;

//
cog ExampleInitCog
{
  configs
  {
    config : Tappy<example5::ExampleConfig>;
  }
  states
  {
    python_state: PythonState
    {
      mutable: true;
    }
  }
  outputs
  {
    output: Tappy<example2::SimpleSchema>;
  }
  execution
  {
    execute when: init;
  }
}
```

The dial for the generated cog goes into a target named `<source_stem>_clk_py_dial`.
The code to for the cog implementation needs to go into a Bazel target named `<source_stem>_clk_py_impl`.

## Generating python executables

The `py_exe` tag tells the compiler to generate code for a python executable.
A Python executable is a C++ executable wrapped in a python binary that sets up the python environment and handles the python dependencies before using `exec` to run the C++ binary.
The compiler will generate an executable whose casing contains all of the boxes declared in the source file.
At least one box is required to generate a C++ executable.

The following example declares a box to create an instance of the python cog declared in the previous example and run then configures the cog to run on a CPU.

It needs some extra stuff to declare a CPU domain and create a channel for the output from the initialization cog.
In particular, you need to import both `cpp` and `py_cog` for the python cog to tell the compiler about the python dependencies for the python cog dial and python cog implementation.
See the [schemas, representations, and interfaces concept guide](../concepts/schema_repr_iface.md) for mode details.

```python
// example8.clk: Example C++ executable

use[cpp] clockwork::python::python_state::{PythonState};
use[cpp, proto, proto_conv] clockwork::example::example5;
use[cpp, py_cog] clockwork::example::example6;

cpu_domain LocalHost;

// Example output channel
channel ExampleOutputChannel
{
  name: "/example/output";
  message_type: Tachyon<example2::SimpleSchema>;
  max_num_messages: 10;
}

box ExampleCogs
{
  new init_cog: example6::ExampleInitCog;

  new memory: HeapMemory(max_size=300'000'000);
  new config: SerializedDataFile(representation=Protobuf<example5::ExampleConfig>, path="path/to/file/example_config.pbtxt");
  new python_state: State(representation=PythonState, memory_resource=memory, init=init_cog.python_state);

  connect config to init_cog.config;
  connect init_cog.output to ExampleOutputChannel;
}

box ExampleExe
{
  new cogs_box: ExampleCogs;
  new example_proc: Process(executable=example8_clk_exe);
  apply HostProcess(process=example_proc) in cogs_box;
  apply HostCpuDomain(cpu_domain=LocalHost) to cogs_box;
}
```

One thing to note is that in the line to create `example_proc` the executable parameter is the name of the executable generated from the example file, in this case `example8_clk_exe`.

## System targets

Clockwork does not support defining a `system_target` in a file with a `generate` attribute.
The recommended practice is to put everything except the system target in files with `generate` attributes, and then use a separate Clockwork file to declare the `system_target`.
