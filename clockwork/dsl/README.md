# Clockwork DSL

The Clockwork domain-specific language (DSL) (also referred to as just "Clockwork" when no confusion with the Clockwork framework is likely) is the domain-specific-language at the center of the Clockwork framework.
It's used to define all entities within Clockwork and how they interconnect, including the following main entity types:

- Data schemas and representations of and interfaces to those schemas
- Cogs: the fundamental software components
- Channels: the message-passing interconnections between Cogs
- Modules: hierarchical groupings of Cogs
- Hardware components: CPUs, GPUs, accelerators, memory, and network interconnects
- Systems: complete mappings of Cogs to hardware

## DSL compiler and tooling

### Front-end (parsing)

The syntax is defined in `clockwork.fltkg` and the parser is generated (in Python) automatically from the grammar by the [FLTK](https://github.com/rnortman/fltk) parser generator.
FLTK supports flexible and powerful [PEG](https://en.wikipedia.org/wiki/Parsing_expression_grammar) grammars and generates efficient memoizing [Packrat](https://en.wikipedia.org/wiki/Packrat_parser) parsers with an extension to support [left-recursive](https://en.wikipedia.org/wiki/Left_recursion) grammars.
There is no separate lexing stage required with PEG parsers; the parser operates directly on the source text as a string of characters.

The upshot of all this is that the grammar is free to express the natural structure of the syntax in a natural way without worrying about the parsing algorithm, as is usually necessary when writing grammars for other parsing algorithms, such as LL(k) or LR(K).
And because the parser is auto-generated, nobody needs to write tiresome and error-prone parsing code by hand.

FLTK also generates a set of Concrete Syntax Tree (CST) node classes that can represent the grammar's syntax.
The output of the generated parser is a strict tree of these nodes, where each node has a direct correspondence to a syntactic element, corresponding to a span of characters in the source code.
From any CST node it's possible to retrieve the corresponding source code span.

### Intermediate representation (IR)

The CST generated by the parser is tightly coupled to the syntax and is by necessity a strict tree.
When working with the semantic entities encoded in the DSL, it is inconvenient to be so tightly coupled to the syntax, and this also makes the entire compiler brittle in the face of syntax changes or extensions.
In particular, the semantic entities usually have graph relationships, including cyclic references, which cannot be represented in a strict tree structure.

To provide a better data model for analysis, the next phase of compilation is generation of a semantic intermediate representation ([IR](ir/README.md)).
The IR is a graph structure which has some relationship to syntactic elements (most IR nodes allow traversal to the one or more CST nodes that defined them) but is not structured as a syntax tree, but rather as a semantic entity graph.
Among other things, during the CST-to-IR phase, identifiers in the source code are resolved to the entities they refer to (name resolution), even when these references cross source files, so that analysis of the graph is simple traversal without needing to do any lookups.
This name resolution is a big part of what transforms the tree to a graph, because it can result in cyclic references and other non-tree structures, including references that span across entities defined in multiple source files.

The resulting IR is a data model describing the semantic content of the DSL source code files and should be usable as the starting point for all compilers and tooling related to the DSL, whether they need to generate code or just analyze the system structure.
It should be very rare for tooling to need to deal with the syntax or CST directly, other than the parsing and IR generation phases.
By using the IR as the core data model, we decouple most of the tooling from the syntax details, allowing us to evolve the syntax as needed.
