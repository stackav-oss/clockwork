# Cog Metrics

This is a reference guide to the cog metrics that are generated by the underlying Clockwork infrastructure.
These metrics are captured in the logs and can provide insights regarding the performance and behavior of a cog.

## Metrics To Log

Each time a cog executes, internally within the infrastructure, it stores the following in memory to enable metrics to be logged for events or telemetry:

1. Latency from first ready to execution.
   - The cog first becomes ready when all trigger conditions are met.
     The conditions are checked when the cog receives a notification that an input condition has changed or a timer has expired.
2. Latency from first execution attempt to execution.
   - Once a cog is ready, it may not immediately be executed.
     The primary reason for not being able to run a cog is the cog needs access to mutable state that is currently in use by an already running cog.
3. Number of re-queues before execution.
   - A cog that is ready may not be able to be run yet.
     One reason for this today is requiring mutable state that is in use by an already running cog.
     In this case, the cog is added back to the run queue.
4. Execution duration.
5. Number of new messages per channel (both input and output channels).
6. Value of each trigger condition.


### Per-Cycle Metrics in Event

The metrics above are collected in event logs per execution cycle of each cog.
These will be stored in batches with a default size of 10 and published either when the batch is full or every second (whichever comes first).
For cogs that execute more than 10 times per second the default batch size should be increased in the cog metrics options so that a batch represents a second's worth of executions.
To change the metrics batch size a metrics_options section can be added to the cog definition to increase it or even disable metrics entirely.
In the example below `enabled` is set to true for demonstrative purposes, however that is the default and it does not require being set that way.

```clockwork
cog ExampleCog
{
    metrics_options
    {
        enabled: true;
        batch_size: 100;
    }
}
```

Each element in the batch will contain the following:

- Execution start time: (units 1ns signed)
- Execution duration: (units 10ns unsigned)
- Latency from first ready to execution: (units 10ns unsigned)
- Latency from first execution attempt to execution: (units 10ns unsigned)
- Number of re-queues before execution: (units count)
- Number of unseen messages per input channel: (units count)
- Number of messages per output channel: (units count)
- Value of each trigger condition: 1 byte per 8 triggers (units flag)
- Max delta between newest not seen message and execution time per input channel (message staleness): (units 10ns unsigned)
- Number of messages dropped per input since last execution: (units count)

### Aggregated Metrics in Telemetry

For gathering more data and obtaining a better baseline for each cog, the same metrics aggregated at 1hz will be published to telemetry.

For every execution that ended in the last second:

- Execution duration: min, max, mean: (units 10ns unsigned)
- Latency from first ready to execution: min, max, mean (units 10ns unsigned)
- Latency from first execution attempt to execution: min, max, mean (units 10ns unsigned)
- Number of re-queues before execution: min, max, mean (units count)
- Number of unseen messages per input channel: min, max, mean: (units count)
- Number of messages per output channel: min, max, mean: (units count)
- Value of each trigger condition: (units flag)
- Number of executions: (units count)
- Execution period (duration between this execution start time and previous execution start time): min, max, mean: (units 10ns unsigned)
- Max delta between newest not seen message and execution time per input channel (message staleness): min, max, mean (units 10ns unsigned)
- Number of messages dropped per input since last execution: min, max, mean (units count)

### Metrics Channels

When a cog is declared, a schema is implicitly generated for the metrics that will be logged.
This must be on a per-cog basis because the number of inputs and outputs will vary by cog.

For a system, each cog will get two implicitly created channels on which it will publish metrics.
The channel will be of the form `/_clockwork/journal/execution-metrics/<CogName>/<instance uuid>` and `/_clockwork/journal/aggregated-execution-metrics/<CogName>/<instance uuid>`.
A message called `MetricsChannelMetadataReport` is published to the log as a persistent message.
This report provides a mapping between the metrics channel names and the cog instances that the channel is collecting metrics for.
Under this naming scheme, moving a cog to a new location will change the name of the metrics channel associated which might affect the way we display in dashboards.

```clockwork
// Metrics channel metadata
schema MetricsChannelMetadata
{
  uuid: 914fa7b8-1413-41b2-9798-6d4ff3337753;
  parameters
  {
    // Maximum channel name size
    #0 max_channel_name_size = 300;

  }

  fields
  {
    // Channel name
    #1 metrics_channel_name: VarString<max_channel_name_size>;

    // Channel UUID
    #2 metrics_channel_uuid: Uuid<process_description::EndpointInstanceId>;

    // Cog Path
    #3 cog_path: VarString<max_channel_name_size>;

    // Cog Instance Path
    #4 cog_instance_path: VarString<max_channel_name_size>;
  }
}

// Metrics channel metadata report
schema MetricsChannelMetadataReport
{
  uuid: 03d8a6f0-3574-4235-87b7-30d52b27abda;
  parameters
  {
    // Maximum channel name size
    #0 max_channel_name_size = 300;

    // Maximum channel name size
    #1 max_num_channels = 1023;
  }
  fields
  {
    // Metrics channel metadata
    #2 metrics_channels: VarArray<
      MetricsChannelMetadata<max_channel_name_size>,
      max_num_channels>;
  }
}
```

## Generated Schemas

The metrics for each cog are published using schemas that are automatically generated based on the cog's definition.
This ensures that the metrics data reflects the specific inputs, outputs, and conditions of each cog.

### Event Metrics Schemas

For event metrics, two schemas and an enum are generated for each cog:

1. **`<CogName>ConditionsMask`**: This is a bitmask enum that represents the active trigger conditions for an execution. It has a value for each condition defined in the cog.

2. **`<CogName>EventMetricsBatch`**: This schema is what is actually published on the event metrics channel. It contains a single field, `event_metrics`, which is a variable-sized array of `<CogName>EventMetrics`. The maximum size of this array is determined by the `batch_size` configuration.

3. **`<CogName>EventMetrics`**: This schema represents the metrics for a single execution cycle of the cog.
   - For each input channel, a field of type `InputChannelEventMetrics` is created with the same name as the input channel. This contains:
     - `unseen_messages`: `UInt16`
     - `message_staleness`: `TenNanoseconds` (10ns units)
     - `dropped_messages`: `UInt16`
   - For each output channel, a field named `<output_channel_name>_num_messages` of type `uint16` is created.
   - A field named `trigger_flags` of type `<CogName>ConditionsMask` is created.
   - A field named `common_event_metrics` of type `CogEventMetrics` is created. This contains:
     - `execution_start_time`: `Int64` (1ns units)
     - `execution_duration`: `TenNanoseconds` (10ns units)
     - `ready_to_execution_latency`: `TenNanoseconds` (10ns units)
     - `execution_attempt_to_execution_latency`: `TenNanoseconds` (10ns units)
     - `num_requeues`: `UInt16`

### Telemetry Metrics Schema

For telemetry (aggregated) metrics, a single schema is generated for each cog:

- **`<CogName>TelemetryMetrics`**: This schema represents the aggregated metrics over a 1-second interval.
  - For each input channel, a field of type `InputChannelTelemetryMetrics` is created with the same name as the input channel. This contains:
    - `unseen_messages`: `MinMaxMean<UInt16>`
    - `staleness`: `MinMaxMean<TenNanoseconds>`
    - `dropped_messages`: `MinMaxMean<UInt16>`
  - For each output channel, a field named `<output_channel_name>_num_messages` of type `MinMaxMean<UInt16>` is created.
  - For each condition, a field named `<condition.name>_trigger_vals` of type `UInt16` is created.
    This tallies the number of times the specific condition was true when the cog executed.
  - A field named `common_telemetry_metrics` of type `CogTelemetryMetrics` is created. This contains:
    - `exec_duration`: `MinMaxMean<TenNanoseconds>`
    - `ready_to_exec_latency`: `MinMaxMean<TenNanoseconds>`
    - `attempt_to_exec_latency`: `MinMaxMean<TenNanoseconds>`
    - `requeue_count`: `MinMaxMean<UInt16>`
    - `execution_count`: `UInt16`
    - `exec_period`: `MinMaxMean<TenNanoseconds>`
