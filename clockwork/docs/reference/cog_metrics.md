# Cog Metrics

This is a reference guide to the cog metrics that are generated by the underlying Clockwork infrastructure.
These metrics are captured in the logs and can provide insights regarding the performance and behavior of a cog.

## Overview

Cog metrics are implemented using [signal-based report groups](signals.md).
Two report groups are automatically generated for every non-init cog:

- **`cog_event_metrics_group`** (batched): per-execution event data
- **`cog_telemetry_metrics_group`** (post-aggregated): aggregated telemetry data

Both groups are enabled by default for all non-init cogs with no configuration required.

## Metrics Collected

Each time a cog [executes](../architecture/dynamic_scheduling.md), the infrastructure records the following:

- Latency from first ready to execution.
  The cog first becomes ready when all trigger conditions are met.
  The conditions are checked when the cog receives a notification that an input condition has changed or a timer has expired.
- Latency from first execution attempt to execution.
  Once a cog is ready, it may not immediately be executed.
  The primary reason for not being able to run a cog is the cog needs access to mutable state that is currently in use by an already running cog.
- Number of re-queues before execution.
  A cog that is ready may not be able to be run yet.
  One reason for this today is requiring mutable state that is in use by an already running cog.
  In this case, the cog is added back to the run queue.
- Broad execution duration, including framework work before and after the generated cog body.
- Wall time, total thread CPU time, thread user CPU time, and thread system CPU time spent in the generated cog body only.
- Number of new messages per channel (both input and output channels).
- First sequence number published per output channel in per-cycle event metrics.
- Value of each trigger condition.


## Policy Configuration

Cog metrics are controlled via two policies: `CogEventMetricsPolicy` and `CogTelemetryMetricsPolicy`.
Both are enabled by default.
To customize or disable metrics for a specific cog, apply the corresponding policy.

### Event Metrics Policy

The following fields are available:

| Field          | Default | Description                                    |
| -------------- | ------- | ---------------------------------------------- |
| `enabled`      | `true`  | Whether event metrics are enabled for this cog |
| `batch_size`   | `10`    | Maximum number of events per batch             |
| `min_duration` | —       | Minimum duration of the batching window        |
| `max_duration` | `1s`    | Maximum duration of the batching window        |

For cogs that execute more than 10 times per second, `batch_size` should be increased so that a batch represents a second's worth of executions.

Example — customize batching for a high-frequency cog:

```clockwork
use @clockwork::std::cog_metrics_policy::{CogEventMetricsPolicy};

apply CogEventMetricsPolicy to MyCog
{
    batch_size: 50;
    min_duration: 500ms;
    max_duration: 2s;
}
```

To disable event metrics for a specific cog:

```clockwork
use @clockwork::std::cog_metrics_policy::{CogEventMetricsPolicy};

apply CogEventMetricsPolicy to MyCog
{
    enabled: false;
}
```

### Telemetry Metrics Policy

The following fields are available:

| Field              | Default | Description                                        |
| ------------------ | ------- | -------------------------------------------------- |
| `enabled`          | `true`  | Whether telemetry metrics are enabled for this cog |
| `min_duration`     | —       | Minimum duration of the aggregation window         |
| `max_duration`     | `1s`    | Maximum duration of the aggregation window         |
| `min_observations` | —       | Minimum number of observations before reporting    |
| `max_observations` | —       | Maximum number of observations before reporting    |

Example — customize the aggregation window and observation thresholds:

```clockwork
use @clockwork::std::cog_metrics_policy::{CogTelemetryMetricsPolicy};

apply CogTelemetryMetricsPolicy to MyCog
{
    min_duration: 500ms;
    max_duration: 2s;
    min_observations: 5;
    max_observations: 200;
}
```

To disable telemetry metrics for a specific cog:

```clockwork
use @clockwork::std::cog_metrics_policy::{CogTelemetryMetricsPolicy};

apply CogTelemetryMetricsPolicy to MyCog
{
    enabled: false;
}
```

## Per-Cycle Metrics (Event Report Group)

The `cog_event_metrics_group` uses a batched reporting strategy.
Metrics are stored in a VarSoa structure and published either when the batch is full or when the maximum duration elapses (whichever comes first).

Each element in the batch contains:

- `cog_exec_start_time`: Execution start timestamp (`SyncTime`)
- `cog_exec_duration`: Broad duration of cog execution, including framework work outside the generated cog body (`TenNanoseconds`)
- `execute_cog_wall_duration`: Wall time spent in the generated cog body only (`TenNanoseconds`)
- `execute_cog_thread_cpu_duration`: Total CPU time spent by the cog thread in the generated cog body only (`TenNanoseconds`)
- `execute_cog_thread_user_duration`: User CPU time spent by the cog thread in the generated cog body only (`TenNanoseconds`)
- `execute_cog_thread_system_duration`: System CPU time spent by the cog thread in the generated cog body only (`TenNanoseconds`)
- `cog_ready_to_exec_latency`: Latency from first-ready to execution start (`TenNanoseconds`)
- `cog_attempt_to_exec_latency`: Latency from first execution attempt to execution (`TenNanoseconds`)
- `cog_requeue_count`: Number of re-queues before execution (`UInt16`)
- Per input channel:
  - `<input_name>_unseen_messages`: Count of unseen messages at execution time (`UInt16`)
  - `<input_name>_staleness`: Max delta between newest unseen message and execution time (`TenNanoseconds`)
  - `<input_name>_dropped_messages`: Messages dropped since last execution (`UInt16`)
- Per output channel:
  - `<output_name>_num_messages`: Messages published on this output (`UInt16`)
  - `<output_name>_first_sequence_number`: First sequence number published on this output (`UInt64`)
    - Use `<output_name>_num_messages` to determine whether the sequence-number value is meaningful for a given execution.
- Per condition:
  - `<condition_name>_active`: Whether this execution condition was active at execution (`Bool`)
- Per memory resource:
  - `<endpoint_name>_peak_allocated`: Peak allocation size through the memory resource (`Bytes`)
  - `<endpoint_name>_current_allocated`: Memory allocated at the end of the Cog's execution (`Bytes`)
  - `<endpoint_name>_total_allocated`: Total of all allocations during Cog execution (`Bytes`)
  - `<endpoint_name>_total_deallocated`: Total of all deallocations during Cog execution (`Bytes`)

## Aggregated Metrics (Telemetry Report Group)

The `cog_telemetry_metrics_group` uses a post-aggregated reporting strategy.
Metrics are aggregated over a 1-second window by default and published with min, max, and mean values.

Each message contains:

- `execution_count`: Number of cog executions in the aggregation window (`UInt16`)
- `execution_interval`: Duration over which signals were collected (`Duration`)
- `agg_cog_exec_duration`: Broad duration of cog execution, including framework work outside the generated cog body (min/max/mean of `TenNanoseconds`)
- `agg_execute_cog_wall_duration`: Wall time spent in the generated cog body only (min/max/mean of `TenNanoseconds`)
- `agg_execute_cog_thread_cpu_duration`: Total CPU time spent by the cog thread in the generated cog body only (min/max/mean of `TenNanoseconds`)
- `agg_execute_cog_thread_user_duration`: User CPU time spent by the cog thread in the generated cog body only (min/max/mean of `TenNanoseconds`)
- `agg_execute_cog_thread_system_duration`: System CPU time spent by the cog thread in the generated cog body only (min/max/mean of `TenNanoseconds`)
- `agg_cog_ready_to_exec_latency`: Latency from first-ready to execution start (min/max/mean of `TenNanoseconds`)
- `agg_cog_attempt_to_exec_latency`: Latency from first execution attempt to execution (min/max/mean of `TenNanoseconds`)
- `agg_cog_requeue_count`: Number of re-queues before execution (min/max/mean of `UInt16`)
- `cog_exec_period`: Period between consecutive executions (min/max/mean of `TenNanoseconds`)
- Per input channel:
  - `agg_<input_name>_unseen_messages`: Count of unseen messages (min/max/mean of `UInt16`)
  - `agg_<input_name>_staleness`: Message staleness (min/max/mean of `TenNanoseconds`)
  - `agg_<input_name>_dropped_messages`: Messages dropped (min/max/mean of `UInt16`)
- Per output channel:
  - `agg_<output_name>_num_messages`: Messages published (min/max/mean of `UInt16`)
- Per condition:
  - `<condition_name>_active_count`: Number of times the condition was active in the window (value of `UInt16`)
- Per memory resource:
  - `agg_<endpoint_name>_peak_allocated`: Peak allocation size through the memory resource (`Bytes`)

> [!NOTE]
> Shared signal entries in the telemetry group are prefixed with `agg_` to avoid identifier collisions with the event group in the generated signal API.

## Metrics Channels

Each cog gets two implicitly created channels on which it publishes metrics.
The channels follow the naming pattern:

```text
/_clockwork/report-groups/<CogName>/cog_event_metrics_group/<instance-uuid>
/_clockwork/report-groups/<CogName>/cog_telemetry_metrics_group/<instance-uuid>
```

The `<instance-uuid>` is the cog instance's UUID from the system's UUID registry.
This ensures that the channel name is directly tied to the cog instance identity.

## Generated Schemas

The metrics for each cog are published using schemas that are automatically generated based on the cog's definition.
This ensures that the metrics data reflects the specific inputs, outputs, and conditions of each cog.

### Event Metrics Schemas

For event metrics, two schemas are generated per cog:

- **`<CogName>_cog_event_metrics_group_Signal`**: An SoA-enabled schema representing a single execution cycle.
  For each signal, a field is created with the signal's pre-aggregation type.
  MEAN pre-aggregation is expanded to SUM and COUNT fields, since mean can be computed from sum/count in post-processing.
  Fields follow the naming pattern `<signal_entry_name>_<pre_aggregation>`.

- **`<CogName>_cog_event_metrics_group`**: The outer schema published on the event metrics channel.
  It contains:
  - `execution_interval`: Duration over which signals were collected (`Duration`)
  - `signals`: A `VarSoa` container holding batched signal values, with a maximum size determined by `batch_size`

### Telemetry Metrics Schema

For telemetry metrics, a single schema is generated per cog:

- **`<CogName>_cog_telemetry_metrics_group`**: The schema published on the telemetry metrics channel.
  It contains:
  - `execution_count`: Number of cog executions in the aggregation window (`UInt16`)
  - `execution_interval`: Duration over which signals were collected (`Duration`)
  - For each signal entry, fields for each combination of pre-aggregation and post-aggregation (min, max, mean), following the naming pattern `<signal_entry_name>_<pre_aggregation>_<post_aggregation>`
