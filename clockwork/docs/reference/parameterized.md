# Parameterized Channels, Cogs and Boxes

This document covers using parameters to define channels, cogs and boxes in Clockwork systems.
Refer to [Clockwork 101](../clockwork101.md) for high-level Clockwork concepts.

## Formatted strings

The `fmt!` macro is built in to Clockwork for formatting strings in expressions.
The `fmt!` macro works like a python formatted string using curly braces {} to contain expressions.
In the following example two string values are defined named `prefix` and `suffix`.
Then a value named `example` is defined that adds a `.` between the prefix and suffix.
The value of the `example` variable is "before.after".

```clk
prefix = "before";
suffix = "after";
example = fmt!("{prefix}.{suffix}");
```

### Formatted string functions

There are some built-in functions that can be used in the `fmt!` macro to generate system and CPU specific strings.

### system_file_path_base

The `system_file_path_base` function returns a string prefix for files generated by Clockwork during system composition such as logger configuration files and multi-publisher subscriber cofigurations.

Note that the system file path is only available during the final phase of system composition when the compiler is generating the system files.
Calls to `system_file_path_base()` in other contexts will return "NO_SYSTEM_TARGET".

### system_instance_name

The `system_instance_name()` function returns the name of the `target_system` block that is compiled to generate the system.

Note that the system target name is only available during the final phase of system composition when the compiler is generating the system files.
Calls to `system_instance_name()` in other contexts will return "NO_SYSTEM_TARGET".

### name

The `name` function takes a named entity parameter and returns the name of the named entity.

### snake_case_name

The `snake_case_name` function takes a named entity parameter and returns the name of the named entity in snake_case.

### camel_case_name

The `camel_case_name` function takes a named entity parameter and returns the name of the named entity in CamelCase.

### `short_name`

The `short_name` function converts the named entity name to snake*case and then returns the characters after the last "*" in the snake case string.

### Nullish coalescing

If you have a nonexistent value or a null optional you may use the nullish coalescing operator to replace the value with something else.

```clk
parameters
{
 path_component: Optional<String>;
 other_parameter: String;
}
 // replace with an empty string
 example = fmt!("path/to/config{path_component ?? ''}.textproto")
 // replace with a scoped variable
 example2 = fmt!("path/to/{path_component ?? other_parameter}.textproto")
 // replace with a literal string
 example3 = fmt!("path/to/{path_component ?? 'some_literal_string'}.textproto")
```

### Example

The following example shows how to use the built in functions to get the telemetry writer configuration file generated for the CPU domain named `MyCpu`.

```clk
box ExampleBox
{
  new telemetry_log_writer_config: SerializedDataFile(representation=Tachyon<log_writer_config::LogWriterConfig<>>, path=fmt!("{system_file_path_base()}.{system_instance_name()}.{name(MyCpu)}_telemetry_logger_config.tachyon"));
}
```

## Parameterized Channels

A parameterized channel is defined by adding a `parameters` section to the channel definition.
For example, a completely generic channel could be defined by using parameters to specificy both the channel name, and the message type and the maximum number of messages.

```clk
// Docs.
channel GenericChannel
{
  parameters
  {
    str: String;
    typ: Type;
    num: UInt64;
  }
  name: fmt!("/{some_string}");
  message_type: Tachyon<typ>;
  max_num_messages: some_number;
}
```

There is no need to instantiate generic channels.
An instance of a generic channel can be used wherever a channel name is allowed.
For example, the following example connects the output channel of a cog to a channel named "name" with message type `MyMsg` and 10 message slots.

```clk
box MyBox
{
  ...
  connect my_cog.output_channel to GenericChannel<str="name", type=MyMsg, num=10>;
  ...
}
```

It is also possible to use an assignment statement to name a channel instantiation so the template argumements are only specified once.

```clk
MyChannel = GenericChannel<str="name", type=MyMsg, num=10>;

box MyBox
{
  ...
  connect my_cog.output_channel to MyChannel;
  ...
}
```

Policies can apply to either a generic channel or to a specific instantiation.
If a policy is applied to a generic channel then it will apply to all instantiations except for instantiations that have a specific policy.
For example, this next example creates a policty for `MyChannel` that disables logging, and then creates a policy for a specific instantiation to enable telemetry logging.

```clk
// Disable logging for the generic channel
policy ChannelLoggingPolicy for GenericChannel
{
  log_type = LogType::none;
}

// Enable non-redundant telemetry logging for a specific instantiation
policy ChannelLoggingPolicy for MyChannel
{
  log_type = LogType::non_redundant_telemetry;
}
```

## Parameterized Cogs

A parameters block at the top of a cog definition contains the definitions for any cog parameters.
Cog parameters can be diagnostics group or signal IDs and input/output message types.
A simple example of a parameterized cog could look like this

```clk
cog MyCog
{
  parameters
  {
    group_id: string;
    msg_type: Type;
  }
  inputs
  {
    input: Tappy<msg_type>;
  }
  diagnostics
  {
    group_id: group_id;
  }
}

instantiate MyCogInstance: MyCog<group_id=”my_group”, msg_type=MyMsg>;
```

Then the parameterized cog could be used anywhere a non-parameterized cog is used, the only difference is the parameters.
The cog must be instantiated for each combination of parameters in the file where the cog is declared so that we only compile each cog instance once.

```clk
box MyBox
{
   new my_cog : MyCog<group_id="my_group", msg_type=MyMsg>;
}
```

If a name is given when the cog is instantiated then that name can also be used to make a new cog.

```clk
box MyBox
{
   new my_cog : MyCogInstance;
}
```

The generated dial for a parameterized cog is a templated class named `<cog_name>Dial`.
The compiler also generates a concept named `<cog_name>DialType` that can be used to avoid having use the template parameters when implementing the `execute_cog` function.

```cpp
// my_cog_impl.inl
template <MyCogDialType DialType>
void execute_cog(DialType& dial)
{
  ...
{
```

If you want to use explicit template parameters to define the implementation you can.

```cpp
// my_cog_impl.inl
template<jewels::StringParam group_id, typename msg_type>
void execute_cog(MyCogDial<group_id, msg_type>& dial)
{
  ...
}
```

> [!NOTE]
> When implementing a C++ parametrized you must create a corresponding cog_name_impl.impl/.hh file as opposed to a cog_name_impl.cc file used with regular cogs.

Cogs can also have policies to configure signals.
All policies on parameterized cogs apply to the generic cog.
Policies on specific cog instances are not allowed.

## Parameterized Boxes

Box parameters are defined in a parameters block at the top of the box definition.
Box parameters can be pretty much anything except another box, including CpuDomain, Channel and Process.
A simple parameterized box might be like the following.

```clk
box MyBox
{
  parameters
  {
    group_id: string;
    MessageType: Type;
    shared_state: StateInstance;
  }

  new my_cog : MyCog<group_id=group_id, MessageType=MessageType>;

  connect shared_state to my_cog.state;
}
```

The only time you need to instantiate a parameterized box is when a parameterized box is used directly from a box defined in another Clockwork file.
Parameterized boxes contained in non-parameterized boxes or instantiated parameterized boxes are implicitly instantiated provided the parameterized box and the containing box are defined in the same source file.
Instantiation boxes can be avoided by placing the parameterized boxes inside a non-parameterized box and use the non-parameterized box from the other Clockwork file.
With low boilerplate syntax the compiler will tell you when to instantiate a box with an error saying that the box has not been instantiated.
Boxes are instantiated with the `instantiate` statement.
The following example shows an instantiation for a box defined with low boilerplate syntax.

```clk
#![generate(cpp_exe)]

box MyBox
{
  parameters
  {
    group_id: string;
    MessageType: Type;
  }
  new my_cog : MyCog<group_id=group_id, MessageType=MessageType>;
}

instantiate MyBox<"my_group", MyMsg>;

```

With legacy syntax, the user is required to add every box to the executable casing manually.
Boxes are still instantiated with the `instantiate` statement, but the but the instantiation is done in the declaration for the executable's casing.

```clk
box MyBox
{
  parameters
  {
    group_id: string;
    MessageType: Type;
  }
  new my_cog : MyCog<group_id=group_id, MessageType=MessageType>;
}

cpp_executable my_executable
{
  casing
  {
    instantiate MyBox<"my_group", MyMsg>;
  }
}
```
